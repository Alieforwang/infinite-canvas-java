# 模型同步、自动定价与成本感知路由：落地边界与后续方案

本文记录当前实现与后续演进边界。当前版本采用 **Phase 1 兼容落地方式**：继续使用现有 `model` 表，同时把同一 `modelKey + capability` 的多条记录视为一个逻辑模型，把每条记录视为一条渠道线路。本文中“逻辑模型”是现有表上的分组概念，不表示已经创建了 `logical_model` 表。

## 1. 目标与当前边界

目标仍然是：

- 渠道可从上游模型列表同步线路，按渠道与上游模型幂等；
- 售价在逻辑模型分组内保持一致，线路成本从上游价格快照转换并缓存为人民币记账成本；
- 路由在利润安全、成本策略与渠道负载之间进行选择；
- 自动定价只生成管理员可审阅的建议，不在后台静默修改客户售价。

当前已落地的边界：

- 逻辑模型和线路仍共用 `model` 表；`model_key`、`capability` 用于逻辑分组，`channel_id`、`upstream_model` 标识线路。
- 尚未落地独立的 `logical_model`、`model_route` 表，也没有独立 alias registry。
- 自动发现默认使用上游模型名作为 `modelKey`。跨渠道别名归并仍需人工修改 `modelKey`，不会根据名称相似度自动合并。
- 任务负载覆盖创建、提交、排队、运行、下载、成功、失败、取消、过期、重试和故障转移等状态；每次进入或离开 active 集合都与渠道/模型真实归属配对更新。相关生命周期实现已完成；完整 Maven 测试 268 次通过，包含 28 次生命周期事务、幂等与并发回归。

## 2. 当前数据模型：单 `model` 表兼容方案

当前 `model` 表同时承载逻辑模型字段和线路字段：

- 逻辑分组字段：`model_key`、`capability`、客户售价规则及兼容定价字段；
- 线路字段：`channel_id`、`upstream_model`、`route_weight`、能力/规格、启用状态；
- 成本缓存字段：`cost_per_unit`、`cost_quota_type`、`cost_synced_at`；
- 兼容负载字段：`current_load`。

同一 `modelKey + capability` 是一个逻辑价格组。当前统一传播的五个销售字段为：

1. `pricingRules`
2. `creditsPerSecond`
3. `resolutionFactors`
4. `audioFactor`
5. `minChargeCredits`

传播只更新上述销售字段，不传播线路的渠道、上游模型名、能力位、规格、成本、路由权重或负载。这样可以让同一逻辑组使用统一售价，同时保留各渠道线路的真实规格与成本差异。

`current_load` 仍保留用于兼容、初始化和观测，但当前成本路由选择器使用数据库中按渠道统计的真实 active task 数作为软负载因子，不把 `current_load` 作为硬并发闸门。`channel.max_concurrency` 只作为软负载权重的容量分母；它当前不阻止新任务进入渠道。V7 迁移会按真实 active task 数初始化旧 `current_load`，并补充按 `video_task(channel_id,status)` 与 `(model_id,status)` 的查询索引；管理端列表也使用真实 active count 覆盖旧计数展示。

### 2.1 当前 V7 数据迁移

当前新增的 `V7__logical_pricing_and_channel_load.sql` 仍服务于单 `model` 表兼容方案：

- 按每个 `modelKey + capability` 的最小 `id` 作为旧组 canonical，将五个销售字段对齐到同组线路；
- 按真实 active task 数初始化 `model.current_load`；
- 新增 `video_task(channel_id,status)` 和 `video_task(model_id,status)` 索引，支持真实负载统计；
- seed `pricing.cost_max_age_hours=24` 和 `routing.margin_policy=skip`。

`(channel_id, upstream_model)` 的唯一约束已经由 V1 建立，V7 不重复添加该 unique；部署时只需确认历史数据满足该约束并确认 V7 在目标数据库按序执行。V7 不是 `logical_model/model_route` 拆表迁移，也不引入 alias registry。

V7 会覆盖同组历史线路原先不一致的五个销售字段，以最小 ID 记录为准（包括停用线路）。部署前应备份并审阅差异；当前尚未在真实 MySQL 上执行或验证该迁移。

## 3. 模型同步

### 3.1 已实现流程

管理员同步渠道模型时：

1. 请求上游模型列表；
2. 上游请求完成后获取渠道行锁（`channel ... FOR UPDATE`）；
3. 对每个非空且长度合法的上游模型名，以 `(channel_id, upstream_model)` 查询已有线路；
4. 不存在则创建一条 `model` 线路；
5. 按发现模型名和能力查找逻辑组中的 canonical 线路（`... FOR UPDATE`）；
6. 若找到 canonical 线路，将其 `modelKey`、展示名和上述五个销售字段复制到新线路；规格、能力、渠道和成本字段保留新线路自己的值。

因此，同一渠道重复同步不会重复插入同一上游线路。渠道行锁覆盖同一渠道的并发同步；canonical 行锁保护同一逻辑价格组的读取与销售字段复制。

同步明确区分 `llm`（语言）、`image`（图片生成）、`video`（视频生成）和 `unknown`（待审核）。优先使用上游单一、明确的生成能力元数据，再使用保守的模型 ID 规则；不再以渠道默认能力把所有陌生模型归为视频。GPT/Claude/DeepSeek 等语言模型的视觉理解能力不等于图片生成；元数据冲突或型号无法确定时进入待审核且默认停用。语言模型仅作为管理库存分类，不加入图片/视频创作列表或调度。

重复同步保留已有模型的人工能力分类。历史错分类通过管理端“重新识别现有模型”预览差异后显式确认，不批量静默改写；预览跳过与目标逻辑组五项售价冲突的建议，需先人工统一售价。应用按 ID 顺序锁定库存、校验预览中的模型身份/原能力与当前建议、再次检查目标组和本批次售价；任何漂移或冲突返回 409 并整批回滚。分类修正保留五项售价、规格、启用状态和负载，仅清除派生线路成本。图片/视频缺少可靠规格元数据时仍使用默认规格，语言和待审核模型不填充生成规格及计费默认值；管理员需审核实际功能。模型别名、版本映射和跨提供商语义归并尚未自动化。

### 3.2 当前限制

- 幂等键是 `(channel_id, upstream_model)`，不是别名或供应商语义键；
- 已有线路不会被同步自动删除或停用；上游下线模型需要管理员处理；
- 同步创建的新线路只有默认规格和默认销售字段，无法证明上游实际支持全部默认能力；
- 同步与上游请求分离：锁在拿到上游响应后获取，避免网络请求期间长时间占用数据库锁，但仍需用 MySQL 并发集成测试确认锁顺序和唯一约束行为。

## 4. 上游价格快照与线路成本

### 4.1 已实现事务边界

`UpstreamPriceService` 从公开价格端点获取快照，解析报价后先校验美元兑人民币为有限正数，并采用钱包唯一的历史记账精度 `credit.exchange_per_yuan`。原独立的 `pricing.credits_per_yuan` 不再参与换算，避免成本与余额使用不同单位。成功发布时，在同一事务内完成：

- 更新渠道价格快照；
- 删除并插入该快照的报价明细；
- 将报价转换为人民币内部记账单位的 `cost_per_unit`，并写入线路的 `cost_quota_type`、`cost_synced_at`。

快照、报价明细和派生线路成本要么一起提交，要么一起回滚。网络失败、响应不合法或转换参数无效时，旧快照和旧成本保留，不发布半成品数据。成功快照中缺失、无效或不支持的报价会清除对应线路成本，使其不再被当作新鲜成本使用。

### 4.2 成本来源身份边界

成本快照必须绑定当次请求捕获的渠道 source identity，至少覆盖规范化 URL/protocol、认证信息和 API key 等会改变价格来源的配置。渠道更新这些字段时应在当前渠道行锁内重新读取并比较身份；身份发生变化则清理该渠道线路的成本缓存，旧缓存不能继续作为新鲜成本。

正在进行的价格同步拿到上游响应后，必须在写入快照和线路成本前持有渠道行锁，并重新比较“请求开始时捕获的 source identity”和当前身份。身份不一致时丢弃旧响应，不能让旧 credential 的报价覆盖新来源。渠道连通性测试使用只返回健康结果的专用 mapper，不应把旧价格快照或来源配置写回渠道记录。上述 source identity 捕获、身份变更清理缓存、同步前后身份比较和 health-only mapper 已完成生产实现；服务层来源变更、不可变凭据捕获、真实 mapper XML 和同步期间同站认证配置变更等回归已随完整 Maven 测试通过。


### 4.3 成本单位与新鲜度

成本缓存使用人民币内部记账单位（与钱包一致），并保留上游计费类型：

- quota type `1`：按次成本；
- quota type `2`：按秒成本（视频按任务秒数换算）；
- 其他类型、缺失成本、负成本或超过 `pricing.cost_max_age_hours` 的成本不能作为新鲜成本；零成本是有效成本，最终售价仍受 `minChargeCredits`（通常至少为 1）约束；
- 成本同步时间允许最多五分钟的未来时钟偏差，以容忍服务时钟轻微漂移；更远的未来时间视为无效。

`pricing.cost_max_age_hours` 的接口范围为 `1..8760` 小时，后端会对越界或非法值回退/规范化为默认 24 小时；管理端读取设置时也按同一范围约束。
快照展示有独立的公开报价新鲜度；路由使用线路成本缓存的新鲜度。两者可能因不同步时间而暂时不同，后台 UI 应同时展示来源快照状态和线路成本状态。

### 4.4 定时同步与失败语义

后台按固定间隔为启用的公开价格渠道同步。单个渠道失败只记录日志并保留其原快照。价格同步不是自动改价：它只更新快照和线路成本缓存，不改变客户售价规则。

## 5. 成本感知路由

当前选择器为 `CostAwareRouteSelector`，视频和图片任务共用该成本/利润策略；创建任务时只读缓存，不在请求路径发起上游价格网络请求。

### 5.1 三种策略

通过 `routing.strategy` 配置：

- `profit_first`：默认策略。先过滤不满足最低毛利的已知新鲜成本线路，再使用成本利润因子、配置权重和软负载因子选择；
- `cost_first`：在允许参与的线路中优先最低新鲜成本，仍保留软负载权重；
- `weighted_only`：显式忽略成本和毛利策略，只按配置线路权重选择，适用于管理员明确接受纯权重路由的场景。

未知成本包括缺失、无效、过期或无法按当前规格换算的成本。`routing.margin_policy` 默认是 `skip`：

1. 存在满足最低毛利的已知新鲜线路时，只让这些安全线路参与；
2. 没有安全线路但存在未知/过期线路时，允许未知/过期线路作为降级候选，但这不提供毛利保证；
3. 全部候选都是已知新鲜但低于最低毛利时，拒绝路由并返回“调整售价或路由策略”的业务错误；
4. 已知新鲜但低于最低毛利的线路不会因为普通 fallback 自动参与。

将 `routing.margin_policy` 显式设为 `downweight` 后，可在没有安全线路时让全部候选参与，但风险线路只通过最低权重因子降权。该配置必须被视为风险兜底，而不是毛利保证。

### 5.2 成本、毛利和负载权重

路由候选先经过能力、规格、启用状态和渠道可用性过滤。对有客户售价的任务：

- 新鲜线路成本按 quota type 和任务时长计算；
- 最低毛利阈值决定安全集合；
- `profit_first` 使用从最低毛利到目标毛利的利润因子；达到目标毛利后不再额外放大；
- `cost_first` 选择最低成本集合；
- 前两种策略结合线路配置权重与渠道软负载因子；`weighted_only` 仅按线路配置权重选择，不启用成本与负载策略。

软负载因子按渠道计算：使用该渠道真实 active task 数（包含其他模型线路和历史遗留任务），除以 `channel.max_concurrency` 形成负载比例，再衰减该渠道权重。真实 active count 查询和索引已补齐；它是分流权重，不是硬并发限制。硬并发限制尚未引入。终态事务、重复回调、并发成功/取消竞争、图片超时恢复及事件/审计失败回滚已通过回归；真实 MySQL 的锁顺序与隔离行为仍需集成验证。

### 5.3 关键配置

- `routing.strategy`：`profit_first`、`cost_first`、`weighted_only`；
- `routing.margin_policy`：默认 `skip`，风险降权需显式 `downweight`；
- `pricing.target_margin_percent`：目标毛利；选择器按最低/最高边界约束；
- `pricing.margin_floor_percent`：最低毛利安全线；
- `pricing.margin_ceiling_percent`：目标毛利上限；
- `pricing.cost_max_age_hours`：成本缓存最大有效期；
- `routing.margin_floor_weight_factor`：降权 fallback 的最低利润因子；
- `routing.load_balance_factor`：渠道软负载权重强度。

## 6. 管理端自动定价

当前管理端以 `modelKey + capability` 聚合所有线路，但只把以下线路作为建议价成本来源：线路启用、`routeWeight > 0`、渠道启用且渠道能力包含该线路 capability。停用线路、停用渠道、能力不匹配线路仍保留在逻辑组展示，并产生不可路由告警，不会用其廉价成本拉低可用线路的建议售价：

- 对每条价格规则，视频按 `supportedSeconds`、图片按 `supportedSizes` 筛选可服务线路，再用匹配的新鲜成本生成最低成本建议价；视频的像素尺寸不会被当作 `720p` 等分辨率标签；
- 用同规格可服务线路的最高成本检查最低毛利并展示风险警告；
- 缺失/过期成本会显示警告；某条规则没有匹配的新鲜成本时，整个逻辑组跳过建议，不借用其他时长或尺寸的廉价成本；
- 目标毛利低于最低毛利时拒绝生成建议；目标与下限同时为零时仍可生成建议；
- 音频成本未单独报价、未分别报价的多规格、无法确定计费单位时保守跳过；
- 每个逻辑组只发起一次销售字段更新，后端负责向同组线路传播；
- 应用前必须由管理员显式确认。同步、预览和刷新不会修改客户售价。

管理端读取 `pricing.target_margin_percent`、`pricing.margin_floor_percent`、`pricing.margin_ceiling_percent` 和 `pricing.cost_max_age_hours` 作为当前建议参数；目标毛利输入保留管理员临时调整能力，但只影响本次预览，不等于保存全局设置。成本单位在 UI 中显示为 `¥/次` 或 `¥/秒`：前端只按公开记账精度除一次得到元，不重复进行美元换算。

自动定价的安全语义是“最低成本生成建议、最高成本提示风险”，不是保证所有线路都满足最低毛利。真正的运行时安全网仍由成本感知路由执行。

## 7. 后续拆表与 alias registry（尚未落地）

### 7.1 `logical_model`

后续可创建独立的 `logical_model` 表，唯一键为 `(model_key, capability)`，承载客户可见名称、能力位、规格和五个销售字段。客户报价、用户可见模型列表和统一售价最终应读取该表。

### 7.2 `model_route`

后续可将现有 `model` 表拆为 `model_route`，只承载渠道、上游模型、线路规格、路由权重、成本缓存和可用状态，并通过 `logical_model_id` 关联逻辑模型。迁移必须处理历史任务外键、旧 `model_id` 引用、定价字段迁移和回滚策略。

### 7.3 alias registry

后续应增加显式 alias registry，而非继续依赖字符串相等或模糊匹配。建议记录：供应商/渠道、上游模型名、规范化逻辑模型键、能力、版本、生效状态和人工确认来源。同步时先按 `(channel, upstream_model)` 幂等，再按已确认 alias 关联逻辑模型；未知 alias 应进入待审核队列，不应自动改变已有逻辑模型。

拆表和 alias registry 属于后续迁移范围。当前单表实现不应在部署说明中写成已完成的逻辑模型表设计。

在独立逻辑模型表上线前，保持现有 API 契约和 `model` 表引用可用。拆表时先建立双读/双写或可回滚迁移，再逐步将报价、模型列表、任务路由和管理端切换到逻辑模型与线路的明确边界。任何 alias 自动归并、售价传播或成本策略变更，都必须保留管理员可见的审计记录和可回滚路径。

## 11. 人民币金额制度与 V8 兼容迁移

### 11.1 单一金额口径

管理端与用户端使用人民币元，显示 `¥`/`元`；充值、赠送、调账、兑换金额与销售规则输入均以元填写。内部已有 `credits` 字段、整数账本及 API 字段名保持兼容，它们代表内部记账单位，不再作为用户可见的积分制度。

唯一换算精度为历史 `credit.exchange_per_yuan`（默认 100，每元内部单位数）；正整数历史值继续有效，尤其不能将自定义 1000 的系统按 100 换算。该精度冻结为只读，管理端设置接口拒绝修改，防止把所有历史余额整体重新估值。后端按严格正整数 long 解析，无效或缺失配置统一规范化为既有默认 100 并明确返回。前端必须等公开金额配置读取成功后才挂载金额界面；接口精度缺失、无效或超过 JavaScript 安全整数范围时阻止金额操作并允许重试，不自行回退到 100。`pricing.credits_per_yuan` 已弃用；成本、钱包和销售建议全部使用同一个精度。

- 显示：`人民币元 = 原始记账单位 / exchangePerYuan`；例如默认精度下 80 单位显示 `¥0.80`，精度 1000 下显示 `¥0.08`。
- 输入：`记账单位 = 人民币元 × exchangePerYuan`；金额控件保留十进制字符串，以精确运算校验新增或修改金额，提交前必须符合整数精度且处于安全整数范围，不能静默四舍五入、钳位、向上取整或把无效输入改为零。带有循环小数的历史换算比例（如 3）下，未修改的表单金额保留原整数单位，不经有损浮点往返；比较原显示值时也不先转为 Number，避免更长的小数被误判为未修改。
- 兼容历史模型小数费率：旧 `creditsPerSecond` 和规格报价可包含小数内部单位。未修改时保留原费率，规格按尺寸/分辨率与时长识别，未修改的规则保留原 JSON；最终扣费仍执行后端既有向上取整和最低金额规则。语言与待审核模型的编辑页不要求生成规格或创作售价。
- 成本缓存允许小数内部单位，前端应保留适当的小数位，不能把小额成本或自定义精度的钱包余额强行显示为零。
- `plan.priceAmount`/订单实付金额原本就是人民币元，不能再除以精度；套餐到账与赠送额度等 `credits` 字段才需转换。
- 公共设置与账户响应明确携带 `currency=CNY`、`currencyUnit=元` 和 `exchangePerYuan`。前端先载入金额精度；初始化请求失败应提供重试，不可静默猜测默认精度展示可能错误的金额。
- 公开金额配置是跨端接口：管理端布局同样以管理员 token 请求 `GET /api/public/settings`。`/api/public/**` 等 `permitAll` 接口不做 audience 校验，管理端与用户端 token 均可读取；`/api/admin/**` 与用户受保护接口仍按 audience 严格隔离。
- API 既有 `heldCredits`、`settledCredits`、报价/余额与账单字段仍返回原始单位；仅 UI 边界换算一次。扣费、终态 CAS、退款、幂等与事务逻辑不重写。

### 11.2 迁移范围与上线次序

`V8__rmb_presentation.sql` 不缩放或重写历史账户、交易、冻结金额、套餐额度、售价或任务扣费。仅补齐缺省精度说明、弃用独立成本兑换率、替换完全匹配的示例套餐文案，并在旧成本兑换率与钱包精度不一致时清除派生模型成本缓存，等待成功同步后重建；原始上游报价和已确认销售价保留。若值的字符串形式不一致也会保守刷新缓存。

部署前备份并核对原 `credit.exchange_per_yuan`、余额、赠送额度、售价与成本比例；按序执行 V7/V8，注意 V7 自身会统一历史组价。后端与两套前端需一起升级，待公开精度读取成功后使用新金额界面。若 V8 清除了成本缓存，先重新同步上游价格并审阅建议，再确认自动定价；缓存刷新前成本路由仍遵循未知成本的既有策略，不能视为利润保证。

当前迁移回归使用 H2 的 MySQL 兼容模式；它不能替代目标 MySQL 的真实迁移、锁、隔离级别和并发验证。此轮不连接生产数据库或替用户执行上线迁移。
